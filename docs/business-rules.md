# Пользователи

- **BR-USERS-001.** Имя/ФИО пользователя обязательны.
- **BR-USERS-002.** ✅  Уникальность email обеспечивается индексом
  `UNIQUE (lower(email)) WHERE deleted_at IS NULL`, а не `UNIQUE`
  на самой колонке. Поле email хранит исходное написание. 
- **BR-USERS-003.** Email подтверждается. Запись о пользователе можно
  создать, но она неактивна (`is_active=false`), пока почта не подтверждена. Фиксируется
  в поле `email_verified`.
- **BR-USERS-004.** ✅ Email уникален среди неудалённых пользователей
  (`deleted_at IS NULL`). После мягкого удаления email может быть
  переиспользован новым пользователем.
- **BR-USERS-005.** ✅ Пароль хранится в БД только в захешированном виде.
- **BR-USERS-006.** ✅ Пользователь может иметь несколько ролей.
- **BR-USERS-007.**  Пользователь не может остаться без единой роли.
- **BR-USERS-008.** Пользователь может иметь индивидуальные права поверх ролей.
- **BR-USERS-009.** Пользователь может создавать организации.
  Владелец — тот, кто создал (`organizations.owner_id`).
  Пользователь может состоять в организациях, которые создал сам
  или его родитель. Организации других веток иерархии недоступны.
- **BR-USERS-010.** Пользователь имеет статус активности `is_active`.
  Флаг управляется пользователями-родителями компании, а также зависит от подтверждения `email`
- **BR-USERS-011.** Удаление пользователя мягкое (`deleted_at`).
  Мягкое удаление родителя каскадно применяется ко всему поддереву
  его дочерних пользователей.
- **BR-USERS-012.** При мягком удалении пользователя его организации
  удаляются физически (CASCADE на `user_organizations`).
- **BR-USERS-013.** Владелец организации автоматически добавляется
  в `user_organizations` при создании организации.
- **BR-USERS-014.** Родитель не видит организации, созданные его
  дочерними пользователями.





# Организации

- **BR-ORG-001.** Организация создаётся пользователем. Владелец
  организации — создатель (`organizations.owner_id`). Необходимое
  право на создание определяется в модели прав (BR-USERS-008).
- **BR-ORG-002.** Организация обязательно имеет:
  - наименование (`name`);
  - ИНН (`inn`);
  - владельца (`owner_id`).
  Адрес (`address`) — опционален.
- **BR-ORG-003.** ИНН уникален глобально (в пределах всей системы).
- **BR-ORG-004.** Наименование организации уникально в пределах
  одного владельца (`owner_id`). Одно и то же название у разных
  владельцев — допустимо.
- **BR-ORG-005.** Владелец автоматически добавляется
  в `user_organizations` при создании организации.
- **BR-ORG-006.** Организация может включать одного или нескольких
  пользователей, и пользователь может иметь доступ к нескольким организациям одновременно.
- **BR-ORG-007.** Организации удаляются физически. Мягкое удаление
  к справочным данным не применяется.
- **BR-ORG-008.** ✅При удалении владельца его организации удаляются
  физически (CASCADE на `user_organizations`).
- **BR-ORG-009.**✅ При удалении организации её связи
  с пользователями (`user_organizations`) удаляются физически.
- **BR-ORG-010.** Управлять организацией (добавлять пользователей,
  изменять, удалять) может только владелец.
- **BR-ORG-011.** Родитель не может удалить организацию своего
  дочернего пользователя (следствие BR-USERS-014).


# Доступы

### Источники прав

- **BR-ACCESS-001.** У пользователя два источника прав:
  - роли (шаблоны);
  - прямые права (индивидуальные).
- **BR-ACCESS-002.** Роль — это набор вариантов прав. Роль только
  добавляет доступ, не ограничивает.
- **BR-ACCESS-003.** Прямое право — индивидуальное назначение
  варианта права пользователю. Может быть разрешающим
  (`effect = ALLOW`) или запрещающим (`effect = DENY`).
- **BR-ACCESS-004.** Условия задаются на варианте права
  (`PermissionCondition`), а не на связи.

### Право и вариант права

- **BR-ACCESS-005.** `Permission` — атомарное право. Определяется
  парой `resource + action`. Immutable, не меняется.
- **BR-ACCESS-006.** `Permission.code` генерируется автоматически
  по шаблону `{resource}.{action}`.
- **BR-ACCESS-007.** `PermissionCondition` — вариант права. Определяет
  объём доступа: `type` (all | category | role | creator)
  и `effect` (ALLOW | DENY).
- **BR-ACCESS-008.** `PermissionCondition` — immutable. Изменение
  невозможно. Только создание или удаление.
- **BR-ACCESS-009.** Комбинация `(permission_id, type, effect,
  category_id, role_id)` уникальна.
- **BR-ACCESS-010.** `is_active = false` — вариант выключен.
  Связи сохраняются. Authorization пропускает неактивные варианты.
- **BR-ACCESS-011.** Формат прав: `сущность.операция.условие`.

### Типы условий

- **BR-ACCESS-012.** `type = all` — право действует на весь ресурс.
- **BR-ACCESS-013.** `type = category` — право действует на конкретную
  категорию (`category_id`).
- **BR-ACCESS-014.** `type = role` — право действует в отношении
  конкретной роли (`role_id`).
- **BR-ACCESS-015.** `type = creator` — право действует только
  на объекты, созданные текущим пользователем.
- **BR-ACCESS-016.** Список типов — системный. Пользовательские
  типы не добавляются.

### Эффекты

- **BR-ACCESS-017.** `effect = ALLOW` — разрешает доступ.
- **BR-ACCESS-018.** `effect = DENY` — запрещает доступ.
- **BR-ACCESS-019.** `DENY` имеет приоритет над `ALLOW`.
- **BR-ACCESS-020.** `DENY` может быть задан только в прямых правах
  (`UserDirectPermission`). Роли не могут запрещать.
- **BR-ACCESS-021.** `DENY` без условий (`type = all`) — запрещает
  право полностью.
- **BR-ACCESS-022.** `DENY` с условиями (`type = category` или
  `role`) — запрещает объекты, удовлетворяющие условию.

### Связи

- **BR-ACCESS-023.** `RolePermission` — связь роль ↔ вариант права.
  Ссылается только на `effect = ALLOW`.
- **BR-ACCESS-024.** `UserDirectPermission` — связь пользователь ↔
  вариант права. Может ссылаться на `ALLOW` и `DENY`.
- **BR-ACCESS-025.** `UserPermission` — материализованный итог.
  Ссылается на все варианты (и `ALLOW`, и `DENY`).

### Синхронизация

- **BR-ACCESS-026.** Синхронизация запускается при любом изменении
  связей: `RolePermission`, `UserDirectPermission`.
- **BR-ACCESS-027.** Изменение связи и синхронизация выполняются
  в одной транзакции.
- **BR-ACCESS-028.** При синхронизации для каждого пользователя:
  1. Собрать все `condition_id` из ролей пользователя.
  2. Собрать все `condition_id` из прямых прав пользователя.
  3. Записать объединение в `UserPermission`.
- **BR-ACCESS-029.** Если один и тот же `condition_id` пришёл
  из роли и из прямого права — в `UserPermission` одна запись.
- **BR-ACCESS-030.** Удаление `PermissionCondition` каскадно удаляет
  связи и записи в `UserPermission`.

### Authorization

- **BR-ACCESS-031.** Authorization читает только `UserPermission`.
  Роли и прямые права в проверке не участвуют.
- **BR-ACCESS-032.** Для каждого запроса:
  1. Найти все `UserPermission` для `(user_id, permission_id)`.
  2. Пропустить условия с `is_active = false`.
  3. Если хотя бы одно `DENY`-условие сработало — отказ.
  4. Если хотя бы одно `ALLOW`-условие сработало — доступ.
  5. Иначе — отказ.
- **BR-ACCESS-033.** Проверка условия `type = creator` — программная:
  создатель объекта совпадает с текущим пользователем.
- **BR-ACCESS-034.** Проверка условия `type = category` — программная:
  категория объекта входит в разрешённые.
- **BR-ACCESS-035.** Проверка условия `type = role` — программная:
  роль, указанная в условии, участвует в операции
  (например, назначается пользователю при `users.create`).

### Управление правами

- **BR-ACCESS-036.** Список ресурсов и действий фиксирован в коде.
- **BR-ACCESS-037.** Ресурсы: users, roles, products, categories,
  templates, quotes, projects, customers, suppliers, media,
  calculator, settings, audit_log.
- **BR-ACCESS-038.** Действия: create, read, update, delete, archive,
  export, import.
- **BR-ACCESS-039.** Действие `archive` включает восстановление
  из архива.

### Удаление

- **BR-ACCESS-040.** Физическое удаление `Permission` каскадно
  удаляет все связанные записи.
- **BR-ACCESS-041.** Системное право (`is_system = true`) удалить
  нельзя.
- **BR-ACCESS-042.** `PermissionCondition` удаляется физически.
  Мягкое удаление не применяется — для этого есть `is_active`.



# Роли

- **BR-ROLE-001.** Роль — набор вариантов прав (`PermissionCondition`).
  Роль только добавляет доступ, не ограничивает.
- **BR-ROLE-002.** Роль не имеет иерархии. Роли не наследуются
  друг от друга.
- **BR-ROLE-003.** Роль глобальна, не привязана к организации. (BR-ORG)
  Роль распространяется на пользователя независимо от того,
  в каких организациях он состоит.
- **BR-ROLE-004.** Системная роль — «Системный администратор».
  Содержит все права. Не редактируется и не удаляется.
- **BR-ROLE-005.** Пользовательские роли создаются пользователем,
  имеющим право `roles.create.all`.
- **BR-ROLE-006.** Роль имеет владельца (`owner_id`) — того, кто её создал.
- **BR-ROLE-007.** Имя роли уникально в пределах владельца
  (`UNIQUE (owner_id, name)`).
- **BR-ROLE-008.** Пользователь может иметь несколько ролей
  (BR-USERS-005).
- **BR-ROLE-009.** Пользователь не может остаться без роли
  (BR-USERS-006).
- **BR-ROLE-010.** Пользователь не может назначить роль сам себе.

### Изменение и удаление

- **BR-ROLE-011.** Роль изменяется пользователем, имеющим право
  `roles.update.subtree`.
- **BR-ROLE-012.** Роль деактивируется через `is_active = false`.
  Мягкое удаление (`deleted_at`) не применяется.
- **BR-ROLE-013.** Роль нельзя деактивировать, если под ней есть
  хотя бы один пользователь. Сначала нужно снять роль со всех
  пользователей.
  - **BR-ROLE-014.** Проверка «нет пользователей под ролью»
  выполняется в сервисном слое (ADR-ROLE-005).
- **BR-ROLE-015.** Нельзя снять роль с пользователя если эта роль - единственная под ним.
- **BR-ROLE-016.** Проверка «не единственная роль»
  выполняется в сервисном слое (ADR-ROLE-005).
- **BR-ROLE-017.** Связь `user_roles` не имеет `deleted_at`.
  Снятие роли с пользователя — физическое удаление строки
  из `user_roles`.

### Иерархия и доступ

- **BR-ROLE-018.** Родитель видит все роли дочерних пользователей,
  создание которых ему доступно.
- **BR-ROLE-019.** Родитель может изменять роли дочерних
  пользователей через `users.update` (изменение поля ролей
  пользователя). Сущность Role при этом не меняется —
  меняется связь `user_roles`.
- **BR-ROLE-020.** Родитель может снять роль с дочернего
  через `users.update`. Сущность Role не удаляется.
- **BR-ROLE-021.** Роль не назначается пользователю из другой ветки
  иерархии.

### Назначение ролей

- **BR-ROLE-022.** Роль назначается пользователем, имеющим право
  `users.create` с `type = role` и указанием конкретной роли.
- **BR-ROLE-023.** `users.create` с `type = all` позволяет назначать
  любую доступную правами роль при создании пользователя.
- **BR-ROLE-024.** Роль назначается только в пределах ветки иерархии
  (родитель → дочерний).
- **BR-ROLE-025.** При создании пользователя выбирается роль
  из списка. Дополнительно можно настроить индивидуальные права
  через `user_direct_permissions` (ALLOW и DENY).

### Пакет прав

- **BR-ROLE-026.** Право `roles.create.all` поставляется вместе
  с `roles.update.subtree` и `roles.delete.subtree`. По отдельности
  они не имеют смысла.
- **BR-ROLE-028.** `subtree` в правах `roles.update.subtree`
  и `roles.delete.subtree` означает «роль, владелец которой
  находится в поддереве текущего пользователя (включая самого
  пользователя)». Проверка — рекурсивный обход поддерева.
