# Архитектурные решения

## Сессии

### ADR-AUTH-001. Создание отдельных сессий
Решение: каждая успешная авторизация создаёт новую запись сессии.
Не используется ограничение на количество активных сессий пользователя. Повторная авторизация с другого устройства, браузера или клиента не требует завершения предыдущей сессии.
Пример:
User
 ├── Session A
 ├── Session B
 └── Session C
Каждая сессия является самостоятельной и имеет собственный идентификатор, а также токен.


### ADR-AUTH-002. Отсутствие ограничений по устройству и IP
Решение: система не запрещает авторизацию на основании user_agent или IP-адреса.
user_agent может сохраняться в сессии как дополнительная информация о клиенте, но не используется для запрета создания новой сессии.
Это позволяет не связывать бизнес-правила авторизации с нестабильными характеристиками подключения, такими как IP-адрес.


### ADR-AUTH-003. Cookie и серверная сессия
Решение: cookie содержит токен серверной сессии, а состояние сессии хранится в БД.
Cookie и запись сессии в БД рассматриваются как разные сущности.
Удаление или потеря cookie не означает автоматического удаления сессии из БД. В этом случае существующая серверная сессия может оставаться активной до истечения срока действия.
При повторной авторизации создаётся новая серверная сессия с новым токеном и устанавливается новая cookie.


### ADR-AUTH-004. Проверка авторизации на двух уровнях
Решение: проверка авторизации выполняется на двух уровнях.
• Frontend — для управления пользовательским интерфейсом и навигацией.
• Backend — для фактической проверки доступа к защищённым ресурсам.
Frontend выполняет редирект авторизованного пользователя со страницы логина, но это не является механизмом безопасности.
Backend самостоятельно проверяет наличие и валидность токена сессии для каждого защищённого запроса.


### ADR-AUTH-005. Жизненный цикл сессии
Решение: сессия проходит следующий жизненный цикл:
Создание
   ↓
Активна
   ↓
Продление при активности
   ↓
Logout ──────────→ Удаление
   │
   └──────────────→ Истечение срока → Недействительна


### ADR-AUTH-006. Данные сессии
Сессия должна содержать данные, необходимые для управления её жизненным циклом, в частности:
id
user_id
token_hash          SHA-256 от токена, не сам токен
user_agent          nullable
ip_address          nullable
created_at
expires_at
last_used_at        nullable

Обоснование:
- `id` и токен — разные сущности (см. ADR-AUTH-003);
- `user_agent` и `ip_address` — nullable, не используются для блокировки (см. ADR-AUTH-002);
- `last_used_at` — nullable, NULL означает «никогда не продлевали» (см. ADR-AUTH-007).


### ADR-AUTH-007. Продление сессии
Решение: продление `expires_at` выполняется не чаще одного раза в 24 часа.

Поле `last_used_at` в `sessions` хранит момент последнего продления.
Логика при запросе:
1. `last_used_at = None` → продлить сразу.
2. `now - last_used_at < 24ч` → не продлевать.
3. `now - last_used_at >= 24ч` → продлить: `expires_at = now + 7 дней`, `last_used_at = now`.

Обоснование:
- продление на каждом запросе = `UPDATE` в БД на каждый запрос → лишняя нагрузка, блокировки, рост WAL;
- раз в 24 часа — компромисс: сессия продлевается для активных пользователей, но БД не нагружается;
- `last_used_at` хранится в БД, не в cookie — cookie может быть подделана клиентом.

Источник истины: БД. Cookie клиента не используется для решений о продлении.


### ADR-AUTH-008. Хранение токена сессии

Решение: в БД хранится SHA-256-хеш токена, не сам токен.

Обоснование:
- при утечке БД злоумышленник получит только хеши;
- SHA-256 необратим — восстановить токен нельзя;
- SHA-256 (не bcrypt), потому что токен — высокоэнтропийная случайная строка, bcrypt замедлил бы каждый запрос без пользы для безопасности.

Следствия:
- клиент получает открытый токен в cookie (httpOnly, secure, samesite);
- сервер хеширует токен из cookie и ищет сессию по `token_hash`.
